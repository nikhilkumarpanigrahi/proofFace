# ProofFace — Product Requirements Document (PRD)

**Version:** 1.0  
**Status:** Implementation-ready  
**Primary language:** Rust  
**Target:** HackerHouse Goa 2026 — Shortlisting Task 3  
**Blockchain:** Polygon Amoy Testnet  
**Project type:** Local CLI / end-to-end pipeline  
**Primary constraint:** Real external discovery and real blockchain verification; no hardcoded results in the demo path.

---

## 1. Executive Summary

ProofFace is a Rust-first, end-to-end pipeline that takes a face image as input, detects and encodes the face, performs a genuine search for publicly accessible web/social content, independently verifies candidate content using face similarity, creates a deterministic cryptographic fingerprint of the discovered content, records that fingerprint on a blockchain testnet, and independently verifies the content against the on-chain record.

The project is intentionally designed as a **modular monolith** rather than a collection of microservices. External dependencies are isolated behind provider interfaces so failures can be handled with retries, timeouts, fallbacks, bounded concurrency, and graceful degradation.

The system must never claim a positive verification when evidence is insufficient.

---

## 2. Problem Statement

Finding a public post that contains a particular face and proving later that the discovered content has not been altered are separate problems.

A search result is not proof of identity, and a copied image/post is not necessarily the same content that was originally discovered.

ProofFace combines:

1. Face detection and embedding.
2. Genuine external web discovery.
3. Independent candidate verification.
4. Deterministic content fingerprinting.
5. Blockchain-backed integrity verification.
6. Failure-tolerant orchestration.

---

## 3. Challenge Requirement Mapping

### 3.1 Face Identification

**Required:**

- Accept an input image.
- Detect a face.
- Generate a numerical face representation/embedding.

**Acceptance criteria:**

- Real input image is processed.
- No face produces a clear failure.
- Multiple faces are handled explicitly.
- The resulting embedding is generated by an actual model/runtime.

### 3.2 Web/Social Search

**Required:**

- Perform a genuine search.
- Discover at least one real matching public post/content item.
- Do not use a pre-selected or hardcoded result.

**Acceptance criteria:**

- Search request leaves the local application.
- Returned candidate URLs originate from the external search response.
- Candidate media/content is fetched from the discovered source.
- The application independently checks the candidate face.

### 3.3 Blockchain Verification

**Required:**

- Create a fingerprint/hash of discovered data.
- Record it on a blockchain.
- Recalculate and compare later.

**Acceptance criteria:**

- A real Polygon Amoy transaction is created.
- The transaction stores the proof fingerprint and source identifier.
- The application reads the on-chain record.
- Recalculated fingerprint matches the stored fingerprint for an unchanged record.
- A modified record produces a mismatch.

## 4. Goals

### Primary goals

- Build a working end-to-end pipeline in Rust.
- Use real web discovery.
- Independently verify candidate face similarity.
- Use a real blockchain testnet.
- Make the pipeline resilient to common external failures.
- Keep the codebase modular and understandable.
- Provide a clean CLI suitable for a short screen recording.
- Demonstrate both successful verification and tamper detection.

### Secondary goals

- Demonstrate safe asynchronous concurrency.
- Provide useful structured logs.
- Measure important local performance characteristics.
- Make providers replaceable without rewriting the pipeline.

---

## 5. Non-Goals

The project will not attempt to become:

- A universal facial-surveillance system.
- A private-person tracking system.
- A social-media crawler.
- A production-scale identity database.
- A public SaaS product.
- A website/mobile application.
- A distributed microservice platform.

The demo should use **publicly accessible content and an appropriate/consented test subject**.

---

## 6. Design Principles

1. **Real over simulated.**
2. **Smallest reliable implementation first.**
3. **No silent failures.**
4. **No fabricated verification.**
5. **External dependencies must be replaceable.**
6. **Fail fast for invalid input.**
7. **Use bounded concurrency.**
8. **Never retry indefinitely.**
9. **Never log secrets.**
10. **Measure before optimizing.**
11. **Blockchain proves content integrity, not factual truth.**
12. **Uncertainty results in `UNVERIFIED`, not `VERIFIED`.**

# 8. Functional Requirements

## FR-01 — Image Validation

The system shall:

- Validate that the file exists.
- Validate supported image format.
- Reject corrupted images.
- Enforce reasonable file-size and dimension limits.

Failure state:

```text
INVALID_IMAGE
```

---

## FR-02 — Face Detection

The system shall:

- Detect faces from the input image.
- Report the number of faces.
- Reject zero-face input.
- Handle multiple faces explicitly.

Failure states:

```text
NO_FACE_DETECTED
AMBIGUOUS_FACE_INPUT
```

---

## FR-03 — Face Embedding

The system shall:

- Generate an embedding for the target face.
- Normalize the embedding when required by the model.
- Keep model-specific code isolated inside the face module.

---

## FR-04 — Genuine Search

The system shall:

- Call a real external search provider.
- Receive real candidate results.
- Extract candidate URLs.
- Deduplicate candidates.
- Never substitute a hardcoded result.

---

## FR-05 — Search Provider Abstraction

All search providers shall implement a common interface.

Conceptually:

```rust
trait SearchProvider {
    async fn search(
        &self,
        request: SearchRequest,
    ) -> Result<Vec<SearchResult>, ProviderError>;
}
```

The exact trait may evolve during implementation.

---

## FR-06 — Search Resilience

Search calls shall support:

- Timeout.
- Limited retry.
- Exponential backoff.
- Provider fallback.
- Circuit breaker if justified after the core path works.

The system shall not retry forever.

---

## FR-07 — Candidate Retrieval

For each candidate:

- Validate the URL.
- Fetch accessible content.
- Enforce response-size limits.
- Validate MIME type where possible.
- Handle redirects safely.
- Skip unusable candidates rather than crashing.

---

## FR-08 — Independent Face Verification

The system shall:

1. Process candidate images.
2. Detect candidate faces.
3. Generate candidate embeddings.
4. Compare candidate embeddings to the input embedding.
5. Produce a similarity score.
6. Rank candidates.

Search-provider ranking must not be treated as identity proof.

---

## FR-09 — Match Decision

The system shall use configurable thresholds.

Possible states:

```text
HIGH_CONFIDENCE_MATCH
POSSIBLE_MATCH
NO_MATCH
```

Thresholds must be documented and should be calibrated using appropriate test examples where possible.

The system must not claim universal identity accuracy.

---

## FR-10 — Candidate Deduplication

The system shall avoid processing duplicate candidates where possible.

Potential deduplication keys:

- Canonical URL.
- Media URL.
- Exact content hash.
- Optional perceptual image hash.

---

## FR-11 — Bounded Concurrency

Candidate processing shall use bounded concurrency.

Example:

```text
MAX_CONCURRENT_CANDIDATES=5
```

The exact default may be tuned through benchmarking.

The system must avoid creating an unbounded number of concurrent tasks.

---

## FR-12 — Content Extraction

For the selected candidate, extract available public information such as:

- Source URL.
- Media URL.
- Text/caption where available.
- Relevant metadata.
- Retrieval timestamp.

Only information actually retrieved should be represented.

---

## FR-13 — Canonicalization

The content representation must be deterministic.

Canonicalization should:

- Normalize text encoding.
- Normalize whitespace where appropriate.
- Use deterministic field ordering.
- Exclude volatile fields that should not change the content identity.
- Serialize deterministically.

---

## FR-14 — SHA-256 Fingerprint

The system shall generate a SHA-256 fingerprint from the canonical representation.

Example:

```text
canonical record
      ↓
SHA-256
      ↓
32-byte fingerprint
```

The same canonical record must always generate the same fingerprint.

---

## FR-15 — Smart Contract

Create a minimal Solidity contract that records:

- Fingerprint.
- Source identifier/URL.
- Registration timestamp.
- Optional version/type information.

Do not store the full image on-chain.

---

## FR-16 — Blockchain Submission

The Rust application shall:

1. Create the fingerprint.
2. Submit it to the contract.
3. Wait for transaction confirmation.
4. Store/display transaction hash.
5. Read the resulting on-chain proof.

---

## FR-17 — Blockchain RPC Failover

The application shall support multiple RPC endpoints.

Failure path:

```text
RPC A
 ↓ failure
RPC B
 ↓ success
```

RPC credentials must not be committed.

---

## FR-18 — Idempotent Proof Registration

The system should avoid duplicate proof registration.

The content fingerprint can act as the logical proof identifier.

Before registering:

```text
Does this fingerprint already exist?
```

If yes:

```text
return existing proof
```

If no:

```text
register proof
```

Transaction-uncertainty handling must check chain state before blindly resubmitting.

---

## FR-19 — Read-After-Write Verification

After a successful transaction:

```text
submit
 ↓
confirm
 ↓
read contract
 ↓
retrieve fingerprint
 ↓
recalculate local fingerprint
 ↓
compare
```

Only a successful comparison may produce:

```text
VERIFIED
```

---

## FR-20 — Tamper Detection

If the discovered content is modified after registration:

```text
original fingerprint != recalculated fingerprint
```

the result must be:

```text
TAMPERED
```

---

## FR-21 — Honest Failure

If the system cannot obtain enough evidence:

```text
UNVERIFIED
```

must be returned.

The application must never convert an infrastructure failure into a positive verification.

---

# 9. Non-Functional Requirements

## NFR-01 — Reliability

The system should survive:

- Temporary search failures.
- Temporary RPC failures.
- Individual candidate failures.
- Invalid external content.
- Timeouts.

---

## NFR-02 — Performance

Optimize for:

- Low unnecessary network calls.
- Bounded concurrent candidate processing.
- Early termination when a sufficiently strong match is found.
- Candidate deduplication.
- Efficient embedding reuse where safe.

Network latency and local compute latency should be measured separately.

---

## NFR-03 — Maintainability

Code must:

- Use clear modules.
- Avoid unnecessary abstractions.
- Keep provider-specific code isolated.
- Use structured error types.
- Avoid duplicated logic.

---

## NFR-04 — Security

The application must:

- Never commit private keys.
- Never log private keys.
- Never log API secrets.
- Validate downloaded content.
- Limit download sizes.
- Limit redirects.
- Handle external URLs cautiously.
- Avoid unnecessary storage of personal information.

---

## NFR-05 — Portability

The core Rust application should run locally on the target development machine with documented dependencies.

# 11. Resilience Architecture

## Retry

Use bounded retry with exponential backoff and jitter.

## Timeout

Every network operation must have an explicit timeout.

## Fallback

Use alternate providers/RPCs when primary providers fail.

## Circuit Breaker

Optional after the core pipeline works.

States:

```text
CLOSED → OPEN → HALF_OPEN → CLOSED
```

## Backpressure

Bound candidate processing.

## Bulkhead

Keep resource limits separate for expensive subsystems where useful.

# 16. Blockchain Contract Requirements

The contract should be:

- Small.
- Easy to audit manually.
- Deterministic.
- Easy to query.
- Cheap enough for testnet demonstration.

The contract should not contain face recognition logic.

Face recognition remains off-chain.

Blockchain is used for **content integrity anchoring**.

# 17. Privacy and Safety

The system should only use public/appropriate demonstration data.

The application should not attempt to:

- Identify private individuals.
- Access private accounts.
- Bypass platform access controls.
- Scrape private information.
- Build a persistent identity database.

The demo should clearly distinguish:

```text
Face similarity
```

from:

```text
Verified real-world identity
```
